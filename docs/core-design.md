## 개요

C++ 코어 + Lua 카드 스크립트로 된 위크로스 전용 시뮬레이터를 만든다. 구조는 유프로(YGOPro)를 따르고, 목표는 오리카로 노는 것이다. 이 문서는 채팅에서 정한 설계를 Claude Code에 넘기기 위한 기준서다.

- **범위:** 디바·키·올스타 전 포맷, 최신 룰만. PC 전용.
- **구성:** 코어(C++ 라이브러리) / 프레임(C++ + SDL3 + Dear ImGui, CMake + vcpkg) / 카드 DB(SQLite) / 카드 스크립트(Lua).
- **별개 앱:** 카드 이미지 메이커는 이 문서 범위 밖이다.
- **원본 자료:** `D:\Claude Workspace\WixossArchive` (공식 DB·FAQ·룰 문서 아카이브, `wixoss.db`).

## 아키텍처

코어는 화면을 모르는 순수 룰 엔진이고, 프레임이 당겨 쓰는(pull) 단일 스레드 C API로만 대화한다. 유프로의 ocgcore와 같은 구조다.

**루프**

1. 프레임이 `wx_create_duel(options)`로 대전을 만든다. 옵션: 시드, 포맷, 방 설정, 스키마 버전.
2. 덱을 넣고 `wx_start()`.
3. `wx_process()`를 반복 호출한다. 반환값은 `CONTINUE` / `NEED_RESPONSE` / `END`.
4. `wx_get_messages()`로 쌓인 메시지를 꺼내 그리거나 전송한다.
5. `NEED_RESPONSE`면 플레이어 입력을 `wx_set_response()`로 넣고 3으로.

**원칙**

- **데이터는 콜백으로 받는다.** 카드 데이터 읽기, 스크립트 읽기, 로그를 프레임이나 서버가 제공한다. 코어는 파일을 직접 열지 않는다.
- **결정론.** 같은 시드 + 같은 덱 + 같은 응답 열이면 같은 게임이 나온다. 난수는 코어 내장 PRNG만 쓴다. 리플레이 = 덱 + 시드 + 응답 기록.
- **메시지마다 가시성을 붙인다.** 같은 사건도 받는 사람(P1/P2/관전)마다 다르게 만든다. 서버는 가려서 보내기만 한다(정보 공개 절).
- **스키마 + 버전 협상.** 메시지·응답 포맷은 버전이 붙은 스키마로 정의한다. 생성 시 버전이 안 맞으면 거부한다.
- **선택은 propose → validate.** 코어는 "고를 수 있는 것"과 조건을 보내고, 응답을 검증한다(선택과 입력 절).

**실행 위치**

| 용도 | 코어를 돌리는 곳 | 연결 방식 |
| --- | --- | --- |
| 혼자 테스트·AI 연습 | 내 PC | 프레임이 C API 직접 호출 |
| 온라인 대전 | 방장 PC 또는 중계 서버 | 클라이언트는 메시지만 수신, 상대 비공개 정보는 안 옴 |
| 헤드리스 테스트 러너·AI | 러너 프로세스 | C++ API 직접 링크 |

프레임은 뷰마다 장 모델(YGOPro의 ClientField)을 들고 메시지로 장을 재구성한다. 메시지만으로 모르는 값(효과가 반영된 수치, 덱 속 순서)은 코어를 가진 쪽(혼자 하기의 프레임, 온라인의 방장)이 조회해 UPDATE 메시지로 보충한다. 그래서 게스트와 혼자 하기가 같은 그리기 코드를 쓴다.

## 데이터

카드 데이터는 이미 `wixoss.db`(SQLite)로 나와 있다. 공식 카드 7,156종, 인쇄본 10,828장이고 `build_db.py`가 만든다. 코어는 이 DB를 콜백으로 읽는다.

**테이블**

| 테이블 | 키 | 담는 것 |
| --- | --- | --- |
| `cards` | `cid` | 규칙에 쓰는 수치: 종류·클래스·색 비트·레벨·리미트·파워·비용·그로우 비용·한정 조건·팀·코인·가드·LB 여부·사용 타이밍·출처 |
| `prints` | `cid` + `idx` | 인쇄본(일러) 목록: 키는 (`cid`, `idx`). 카드 번호·세트·레어도·일러스트·이미지·포맷 아이콘. idx 1 = 기본 일러 |
| `texts` | `cid` + `lang` | 이름·읽기·능력 텍스트·LB 텍스트·플레이버. `ja`, `ko` |

- **재록:** 유프로처럼 재록은 한 `cid`로 묶고, 텍스트는 최신 것을 쓴다. 묶는 키는 이름(PR/SP의 「（…）」 접미 제거) + 종류 + 색 + 레벨이다.
- **비용 표기:** 에나는 MTG식 `{W}{R}{U}{G}{B}{C}`, 혼성은 `{W/B}`. 코인 등은 `cost_other` JSON.
- **색 비트:** 백1 젒2 청4 넕8 후16, 0 = 무색.
- **cid 고정:** `cid_map.json`이 카드→cid를 고정해서, DB를 다시 빌드해도 번호가 안 바뀐다.

* **일러 여러 장:** 카드 하나(cid)에 인쇄본을 여러 개 단다. 같은 카드 번호에 이미지가 여러 장이어도 된다. 덱 파일은 카드마다 쓸 idx를 저장하고, 덱 에디터·인게임에서 일러 변경 버튼(또는 휠)으로 고른다. 유프로처럼 일러 때문에 cid를 따로 따지 않는다.
* **동명 취급(`cards.alias`):** 이름은 같고 색·레벨이 달라 cid가 갈린 카드(예: 블랙·그린 카니발)를 대표 cid로 잇는다. "같은 이름 4장"과 포맷 판정이 이걸 본다. 공식 카드는 `build_db.py`가 자동으로 채운다(현재 149장).
* **`card_meta`:** 오리카 제작 정보(제작자·태그·팩·제작일·수정일). 카드 텍스트에는 섞지 않는다.
* **이미지 파일(오리카 팩):** `pics/<cid>.png`(idx 1), `pics/<cid>_2.png`, `pics/<cid>_3.png` …

**cid 대역**

| 대역 | 용도 |
| --- | --- |
| 1 \~ 999,999 | 공식 카드(현재 1\~7,156) |
| 1,000,000 단위 블록 | 오리카 팩 하나당 블록 하나 |
| 예약 블록 하나 | 장 위 비카드 객체(바이러스·게이트·크래프트 등)와 테스트용 |

**데이터 폴더(YGOPro식)**

```
wixoss.db + script/ + formats/ + pics/      최상단: 공식 (YGOPro의 cards.cdb 자리)
repositories/<저장소>/ *.db + script/ + …    저장소 (자동 업데이트, EDOPro식)
expansions/ *.db + script/ + formats/ + pics/  개인 작업물·오리카 (하위 폴더는 안 읽는다)
```

- 로더는 위 순서대로 모든 `.db`를 읽어 합친다. cid가 겹치면 나중에 읽은 쪽이 덮는다(같은 폴더 안은 파일 이름 순).
- `script/`·`formats/`·`pics/`도 같은 순서로 찾고, 뒤쪽이 우선한다.
- **텍스트 언어:** 설정에서 고른다. 고른 언어가 없는 카드는 `ja`로 보여준다. 언어는 프레임 문제라 코어는 `cid`만 다룬다.
- **한글 용어:** 手札=패, 場=장, 引く=뽑는다. 아이콘 코드(【出】《青》 등)는 원문 유지.

## 존과 장

존은 코드에 박지 않고 존 레지스트리에 데이터로 등록한다. 칸 수, 인접, 정면 관계도 모두 데이터다.

**플레이어별 존**

| 존 | 공개 | 순서 |
| --- | --- | --- |
| 메인 덱 | 비공개(카드별 인지 기록) | 있음 |
| 라이프 클로스 | 비공개 | 있음 |
| 루리그 덱 | 본인만 | 없음 |
| 패 | 본인만 | 없음 |
| 트래시 / 루리그 트래시 | 공개 | 없음(집합) |
| 에나 존 | 공개 | 없음(집합) |
| 체크 존 | 공개 | - |
| 제외 영역 | 공개 | 없음 |
| 루리그 존: 센터 + 어시스트 좌·우 | 공개 | 아래 카드 스택은 있음 |
| 시그니 존 × 3(가변) | 공개 | 아래 카드 스택은 있음 |
| 치어 존(개별 존) | 공개 | - |

- **장(場)** = 시그니 존 + 치어 존 + 루리그 존을 묶는 그룹이다(용어집 기준). 효과는 개별 존이나 그룹을 대상으로 지정한다.
- **좌/중/우**는 각 플레이어 기준이다. **정면**은 거울 대칭으로 저장한다(내 왼쪽 ↔ 상대 오른쪽).

* **키**는 루리그 존(루리그 옆)에 놓인다. 루리그가 아니라서 어택할 수 없고, 루리그가 그로우해도 장에 남는다(PR-K011 FAQ).

**가변 시그니 존과 존 부재** (프랙탈 케이지 WXK03-005 FAQ 기준)

- 존에는 고정 ID와 이름이 있다. 인접·정면은 칸 번호로 계산하지 않고 **레지스트리에 저장된 링크**를 쓴다.
- 존을 지우면 `absent` 플래그만 서고, 이름과 링크는 그대로다. 중앙을 지워도 좌·우는 서로 인접하지 않는다.
- 지워질 때 안에 있던 시그니, 붙은 카드(악세·참), 아래 카드, 트랩은 트래시로 간다. 「장을 떠났을 때」 트리거는 발동한다. 바이러스는 사라진다.
- 지워진 동안에는 그 존에 낼 수 없다. 정면 존이 없으면 정면에 시그니가 없는 것으로 보고 데미지가 들어간다.
- 되돌아와도 트래시로 간 카드는 돌아오지 않는다.
- 늘리는 존은 새 ID로 등록하고, 인접·정면 링크는 만드는 효과가 정한다.
- UI는 기본 3칸을 유지하고, 지워진 존에는 × 표시, 늘어난 존은 옆으로 확장해서 그린다.

**장 위 객체**

- 모든 장 위 객체는 **소유자와 컨트롤러를 따로** 갖는다.
- 카드가 아닌 객체(바이러스, 게이트, 하스터릭 WXDi-P05-TK01A, 크래프트 등)는 DB에 예약 블록 cid로 정의하고, 필요하면 Lua를 붙인다. 유프로 토큰과 같은 방식이다.
- **세트 층:** 존마다 트랩·씨앗·매직 박스를 하나씩 둘 수 있는 칸이 따로 있다.
- **존 대상 효과:** 게이트처럼 시그니가 아니라 존 자체에 걸리는 효과를 지원한다.

* WDK09의 게이트 토큰(WDK09-TK-01A)은 공식 DB에 없어서 WXDi-P15-TK01A 【ゲート】를 쓴다.

**플레이어 카운터와 영역**

- 카운터: 코인, 루리그/시그니 배리어, 리미트 어퍼, 구독자 등. 카드가 아닌 표식이라 패로 되돌리는 효과로 제거할 수 없다.
- 플레이어 영역: 비트, 絆 등 어느 존에도 속하지 않는 표식.

## 효과 모델

지속되는 변화는 전부 **효과 객체**로 등록하고, 카드 값은 매번 다시 계산한다. 카드 값을 직접 바꾸는 API는 없다. 이노센스·복사·조커 같은 효과를 여기서 처리한다.

**효과 객체 필드**

- `id`, `owner`, `timestamp`, `reset`(언제 끝나는지)
- **출처 분류:** 인쇄된 【自】【起】·트리거 / 인쇄된 【常】 / 생성된 효과
- **자동 태깅:** `initial_effect`에서 등록되면 "인쇄"다. 복사로 `initial_effect`가 돌아도 인쇄로 본다. 스크립터가 직접 표시하지 않는다.
- **대상 방식:** 고정(특정 객체) 또는 동적(조건에 맞는 것을 매번 검색)

**상태는 효과가 아니다.** 업/다운, 동결, 감염, 크로스, 드라이브, 血晶武装은 카드 플래그다.

**레이어** (숫자 순서로 적용, 같은 레이어 안에서는 타임스탬프 순서)

1. 정체·복사
2. 특성(색, 클래스, 레벨 등)
3. 능력 획득·상실
4. 파워 설정(「X이 된다」)
5. 파워 수정(＋/－)

값을 다시 계산한 뒤 룰 처리(예: 파워 0 이하 배니시)를 돌린다.

**억제 vs 제거**

|  | 억제(何もしない) | 제거(なくなる) |
| --- | --- | --- |
| 대표 카드 | 이노센스 | 복사, 조커 |
| 동작 | 효과는 남아 있고 건너뛴다 | 그 객체에 있던 고정 효과를 삭제한다 |
| 구현 | 억제 효과 자체도 생성된 효과로 등록. 나중 이노센스가 먼저 것을 덮는다 | 삭제 후 되돌리지 않는다 |

**고정 vs 동적 대상** (2024-04 공식 공지)

인쇄된 효과인지 생성된 효과인지가 아니라 **문구**가 정한다.

| 문구 | 대상 | 유프로 대응 |
| --- | --- | --- |
| 「～まで」 | 고정 | `EFFECT_TYPE_SINGLE` |
| 【常】, 「～の間」, 「このターン」 | 동적 | `EFFECT_TYPE_FIELD` + `TargetRange` |

스크립터가 카드마다 골라야 한다. 해석이 바뀌면 전수 조사가 필요하므로, 카드 스크립트에 문구 종류를 주석으로 남긴다.

**객체 동일성**

- 장을 떠나거나 뒷면이 되면 **새 객체**다. 이전 객체에 걸린 효과와 대상 지정은 끊긴다.
- 장 안에서 이동(시그니 존 ↔ 치어 존 등)하면 같은 객체다. 아래 카드와 붙은 카드도 함께 움직인다.

**대체 효과 층**

배리어, 레조나, 크래프트, 슈트, 傀儡状態처럼 "대신 \~한다" 처리는 별도 대체 층에서 가로챈다. 배리어는 데미지만 막고 크러시는 막지 않는다.

## 진행과 타이밍

모든 행동 뒤에는 「룰 처리 → 트리거 처리」 순서가 고정으로 돈다. 페이즈 세부는 아카이브의 룰 문서와 용어집(`guides/text`)을 기준으로 구현한다.

**턴 구조**

1. 업 페이즈
2. 드로우 페이즈
3. 에나 페이즈
4. 그로우 페이즈
5. 메인 페이즈
6. 어택 페이즈: 아츠 사용 단계(턴 플레이어 → 비턴 플레이어, 교대 아님) → 시그니 어택 → 루리그 어택
7. 엔드 페이즈

**룰 처리**

- 11종이 있고, 점검할 게 없을 때까지 반복한다. 트리거보다 먼저 돈다.
- **리프레시는 지연된 룰 처리다.** 덱이 0장이 된 시점이 아니라 룰 처리 타이밍에 일어난다. 턴 플레이어가 한 턴에 두 번째 리프레시를 하면 턴이 끝난다.

**트리거**

- 룰 처리가 끝난 뒤, 대기 중인 트리거를 처리한다. 턴 플레이어 것 먼저, 순서는 그 플레이어가 고른다(매번 묻는다).
- **라이프 버스트도 트리거**로 처리한다.
- 하나 처리할 때마다 룰 처리 → 새 트리거 수집을 다시 돌린다.

**컷인**

- 스펠에만 있다. 스펠 사용 선언 후 상대가 컷인을 할 수 있고, 나중 것부터 해결한다.
- 컷인은 【スペルカットイン】 타이밍을 가진 아츠·능력으로 한다. 하나 처리가 끝나면 다음 것을 선언할 수 있다(faq.txt 「スペルカットイン」).
- 컷인 효과와 스펠 효과 사이에는 룰 처리·트리거를 끼우지 않는다. 스펠 사용이 다 끝난 뒤에 한꺼번에 처리한다(용어집 トリガー能力 2).
- 그 외(아츠, 【起】, 트리거)는 스택이 없다.

**엔드 페이즈**

1. 「턴 종료 시」 트리거
2. 패 6장으로 버리기
3. 「턴 종료 시까지」 효과 종료

강제 턴 종료는 별도의 5단계 절차를 따른다(용어집 ターンを終了する). 2단계에서 버리는 것은 그때 이미 트리거해 있던 능력뿐이고, 3단계(룰 처리)와 5단계(패 버리기)에서 새로 트리거한 능력은 처리한다.

**게임 시작**

- 루리그 덱에는 레벨 0 루리그가 3장 넘게 들어갈 수 있다(용어집 ピース). 시작할 때 레벨 0 루리그 1장 또는 3장을 고른다. 1장뿐이면 자동이고, 3장을 고르면 센터를 따로 고른다.

**기타**

- **LKI:** 장을 떠난 객체를 참조하는 효과는 떠나기 직전 상태를 본다. 코어가 이동 시 스냅샷을 남긴다.
- **데미지 vs 크러시:** 두 개념을 따로 둔다. 배리어는 데미지만 막는다.
- **이벤트:** 기본 이벤트(내기, 어택, 배니시, 이동 등)에 더해, 스크립트가 새 이벤트를 정의해 발생시킬 수 있다.

## 선택과 입력

모든 입력은 하나의 일반 선택 요청으로 통일한다. 대상 고르기, 에나 지불, 모드 선택, 트리거 순서가 같은 방식을 쓴다.

**propose → validate**

1. 코어가 요청을 보낸다: 후보 목록, 최소·최대 개수, 조건 설명.
2. 프레임이 제안을 보낸다.
3. 코어가 검증한다. 틀리면 이유와 함께 거부하고 다시 요청한다.

에나 지불처럼 "이 조합이 비용을 충족하는가"를 미리 다 열거하기 어려운 경우도 검증만 하면 되니까 간단해진다. 프레임의 자동 지불 제안은 코어의 검증 함수를 써서 만든다.

**확정 전 취소(아레나식)**

- 카드 사용 → 대상 → 비용 선택 도중에는 언제든 처음으로 되돌릴 수 있다.
- 코어는 최종 확정 전까지 게임 상태를 바꾸지 않는다. 선택은 임시 버퍼에만 쌓는다.
- 확정 이후에는 되돌릴 수 없다(테스트 모드 제외).

**묻는 시점**

- 쓸 수 있는 카드나 능력이 있을 때만 "쓸 거야?"를 묻는다. 없으면 자동으로 넘어간다.
- 위크로스에서 프리 체인은 스펠 컷인뿐이라 블러프 가치가 없다고 본다.
- 코어는 "항상 묻기"도 옵션으로 지원하고, 기본값만 위처럼 둔다.

**트리거 순서**

- 동시에 여러 개가 트리거되면 매번 묻는다. "결과가 같은 능력"을 코어가 판정하지 않는다.
- 프레임에 "자동 정렬" 편의 옵션을 나중에 둔다.

**행동 열거**

- 각 요청에서 "지금 가능한 행동 전부"를 열거하는 API를 둔다. 헤드리스 테스트와 나중의 대전용 AI가 쓴다.

## 정보 공개

비공개 정보는 코어가 책임진다. 메시지는 받는 쪽마다 따로 만들어지고, 서버는 그대로 나눠 보내기만 한다.

**카드 인지 기록(아레나식)**

- 카드마다 `known_by` 비트(P1, P2)를 둔다.
- "덱 위 3장을 보고 순서를 바꾼다" 같은 효과는 본 사람의 비트를 켠다. 프레임은 "덱 맨 위: 내가 아는 카드"를 표시할 수 있다.
- **셔플하면 초기화한다.**
- 뒷면이 된 카드는 이전에 앞면을 볼 수 있었던 플레이어가 계속 볼 수 있다(예: 시그니가 【트랩】이 됨). 용어집 기준.

**메시지 가시성**

| 받는 쪽 | 보는 것 |
| --- | --- |
| 플레이어 | 공개 정보 + 자기 비공개 정보 + `known_by`에 자기가 있는 카드 |
| 관전(기본) | 공개 정보만 |
| 관전(방 설정: 전부 공개) | 양쪽 패까지 전부 |
| 리플레이 | 게임이 끝난 뒤 전부 |

- 비공개 카드가 이동할 때는 모르는 쪽에는 이동 사실만 보내고 cid는 0으로 가린다.
- 리플레이 파일 = 덱 + 시드 + 응답 기록. 재생 시 코어를 다시 돌려 만든다.

## 포맷과 덱 검증

덱 검증은 포맷마다 Lua 스크립트 하나로 짠다. 새 포맷이나 하우스 룰은 스크립트만 추가하면 된다.
스크립트는 `formats/<포맷>.lua`(덱 파일의 `format` 값: `diva`·`key`·`allstar`)이고, 장 수·같은 이름·시작 루리그 같은 공통 검사는 `formats/common.lua`에 둔다.

**카드 풀**

| 포맷 | 쓸 수 있는 카드 |
| --- | --- |
| 디바 셀렉션 | 디바 아이콘 카드 + 같은 이름의 이전 카드. 레벨 0 루리그는 색과 루리그 타입이 같으면 사용 가능 |
| 키 셀렉션 | 키 또는 디바 아이콘 카드 + 같은 이름의 이전 카드. 레벨 0 루리그는 제한 없음 |
| 올스타 | 전부 |

포맷 아이콘은 `prints.formats`에 있다. "같은 이름" 판정은 cid 기준이 아니라 이름 기준이다.

**덱 구성**

- 메인 덱 40장, 같은 이름 최대 4장, 라이프 버스트 20장 이하.
- 루리그 덱 최대 10장, 같은 이름 중복 불가. 레벨 0 루리그가 3장 이상이면 피스 2장을 추가로 넣을 수 있어 최대 12장.
- 시작 루리그 1장 또는 3장.
- 팀 피스·드림팀 피스는 합계 1장까지.
- 디바 규칙: 같은 루리그 타입의 다른 색 루리그를 한 덱에 넣을 수 없다.

**繭の部屋(금제)**

- 금지 / 2장 제한 / 동시 사용 제한 목록을 데이터로 둔다.
- 기본 적용, 방 설정으로 끌 수 있다.

**테스트 덱**

| 덱 | 포맷 | 루리그 덱 | 메인 덱 | 시작 루리그 |
| --- | --- | --- | --- | --- |
| WXDi-D01 에인션트 서프라이즈 | 디바 | 11(루리그 10, 피스 1) | 40(10종 × 4) | 아토 + 타윌·움르 |
| WDK09 블루 움르 | 키 | 10(루리그 5, 아츠 4, 키 1) | 40 | 움르=놀 |

덱 파일은 `decks/*.json`. 수량 출처는 WIXOSS Wiki(fandom).

## Lua 스크립트

카드 스크립트는 유프로의 이름과 구조를 최대한 따른다(`Effect.CreateEffect`, `SetType`, `SetCode`, `chk==0` 등). 위크로스 고유 개념은 함수와 상수를 새로 추가한다.

- **파일:** `script/c<cid>.lua`, `local s,id=GetID()` + `s.initial_effect(c)`.
- **샌드박스 없음(유프로식).** 스크립트는 방장/서버에서 돌아간다. 필요해지면 나중에 막아도 코어 구조는 안 바뀐다.
- **`aux` 헬퍼:** 처음에는 없이 시작하고, 테스트 덱을 짜면서 3번 이상 반복되는 패턴만 `aux`로 뽑는다.
- **문구 주석:** 지속 효과마다 `-- [まで]` 또는 `-- [の間]`을 남겨, 해석이 바뀌면 grep으로 찾을 수 있게 한다.

**능력 종류 대응**

| 위크로스 | 유프로식 타입 |
| --- | --- |
| 【出】 | `EFFECT_TYPE_SINGLE + TRIGGER_O/F`, `EVENT_ON_PLAY` |
| 【自】 | `TRIGGER_F`(강제) / `TRIGGER_O`(임의), 이벤트별 코드 |
| 【起】 | `EFFECT_TYPE_IGNITION` + 사용 타이밍 제한 |
| 【常】 | `EFFECT_TYPE_SINGLE` / `FIELD` (지속) |
| 라이프 버스트 | `EFFECT_TYPE_LIFEBURST` (트리거로 처리) |
| 아츠·스펠·피스 | `EFFECT_TYPE_ACTIVATE` |
| 【チーム起】 등 팀 능력 | 사용 조건이 붙은 【起】 |

**예시: 대장 토비엘(WXDi-D01-015)의 【自】**

```lua
local s,id=GetID()
function s.initial_effect(c)
  -- 【自】어택 시 다른 시그니 +5000
  local e1=Effect.CreateEffect(c)
  e1:SetType(EFFECT_TYPE_SINGLE+EFFECT_TYPE_TRIGGER_F)
  e1:SetCode(EVENT_ATTACK)
  e1:SetTarget(s.tg1)
  e1:SetOperation(s.op1)
  c:RegisterEffect(e1)
end
function s.tg1(e,tp,eg,ep,ev,re,r,rp,chk)
  if chk==0 then return true end
  Duel.SelectTarget(tp,Card.IsSigni,tp,LOCATION_SZONE,0,1,1,e:GetHandler())
end
function s.op1(e,tp)
  local tc=Duel.GetFirstTarget()
  if not tc:IsRelateToEffect(e) then return end
  -- [まで] 턴 종료 시까지, 대상 고정
  local e1=Effect.CreateEffect(e:GetHandler())
  e1:SetType(EFFECT_TYPE_SINGLE)
  e1:SetCode(EFFECT_UPDATE_POWER)
  e1:SetValue(5000)
  e1:SetReset(RESET_EVENT+RESETS_STANDARD+RESET_PHASE+PHASE_END)
  tc:RegisterEffect(e1)
end
```

함수·상수 이름은 예시다. 실제 API 목록은 테스트 덱 두 개를 짜면서 확정한다.

## 테스트와 AI

룰 정확성은 화면 없이 도는 헤드리스 러너로 검증한다. 테스트 케이스는 공식 FAQ에서 만든다.

**헤드리스 테스트 러너**

- C++ API를 직접 링크하는 콘솔 프로그램이다.
- 케이스 하나 = 시작 상태 + 입력 열 + 기대 결과. 예: "중앙 존이 지워진 상태에서 좌측 시그니가 어택 → 상대에게 데미지".
- 시작 상태는 테스트 모드 명령으로 만든다(아래).
- FAQ 원문은 아카이브의 `cards.json`(카드별 FAQ)과 `guides/text`(용어집·FAQ)에 있다.
- 코어를 고칠 때마다 전체 케이스를 돌린다.

**테스트 모드** (EDOPro 퍼즐·덱 테스트와 같은 개념)

- 카드를 아무 존에나 생성한다.
- 상태를 직접 조작한다: 파워, 라이프, 에나, 코인, 페이즈.
  - 파워는 값을 바꾸지 않고 「그 값이 된다」 효과를 건다(코어 규칙).
  - 라이프·에나는 카드 생성(`wx_test_add_card`)과 이동(`wx_test_move_card`)으로 맞춘다. 페이즈는 시작할 때(`wx_test_begin`) 정한다.
  - 코인은 코인을 구현할 때 넣는다.
- 확정 후에도 되돌린다(`wx_test_undo`).
  - 상태를 바꾸는 입력(덱, 시작, 테스트 명령, 응답)은 전부 입력 기록을 거친다.
  - 되돌리기 = 마지막 응답과 그 뒤 입력을 빼고, 새 대전에서 기록을 다시 실행한다. 스냅숏은 두지 않는다.
  - 프레임은 `MSG_RESET`을 받으면 화면 상태를 비우고, 이어서 처음부터 다시 오는 메시지로 새로 그린다.
- 대전 생성 플래그로만 켜지고, 대전에서는 명령 자체를 거부한다.

**AI**

- **지금:** 테스트용 AI. 행동 열거 API에서 랜덤이나 간단한 규칙으로 고른다. 러너에서 무작위 대전을 수천 판 돌려 크래시·무한 루프를 찾는다.
- **나중:** Windbot 같은 대전용 AI. 클라이언트처럼 메시지를 받고 응답하는 별도 프로그램으로 만든다. 코어 쪽 준비물은 행동 열거 API와 플레이어별 가시성이 전부다.
